VCVio Program Logic Routing
VCVio · investigation record · 2026-10-23

One program logic for VCVio, with cheap routing

Which logic should handle a goal, what core Lean will give on the v4.36 line, and how far automation goes. The answer: vcgen stays the one entry point, behind a syntactic route key, and each layer does what only it can do.

Local branch spike/route-classifier. Base: VCVio main f3df0ac18 + PolyFun re-pin (#911) + the Foxglove bridge spike. Lean v4.35.0; probes also on v4.36.0-rc1 and nightly-2026-10-23.

The answer in brief

Core vcgen

The monadic skeleton: pure, bind, if/match, transformer layers, ∧/∃ splits, invariants and measures, exceptions, and (shown here) separation-logic frames.

VCVio

Averaging steps (core stops at the first +, *, ∑, ∑′), the four event readings, relational logic, handler and bisimulation rules, oracle specs.

PolyFun

Exact WP laws and the ExactWPMonad.dual upper reading. A budget reading would serve query bounds.

Foxglove

Independence and conditioning, for the goals where they are the crux. Its ∗ can ride core frames.

The route key reads head constants only, at about 85µs per goal.

  • Explicit core triples go to core vcgen.
  • Event goals go to their reading, following the reverted prvcgen's table.
  • Relational goals go to rvcgen.
  • Equations between handler-run programs go to bisimulation rules.
  • Query bounds go to a budget reading.
  • Pair events also try Foxglove.

Measured payoff ranges from about 0% to about 70% fewer lines per family. Over the routed part of the library, the estimate is 15–32% fewer lines, which is 7–15% of all proof lines. Heartbeats move 0.3–4.7×, depending on the family.

A large spec library does not change this (section 6, measured on a random sample). Re-proving with today's tools saves 44% of the lines (75% of proof bodies). A ~430-declaration, 4.5k-line spec and handler library adds 1.2 points, and costs more lines than it saves.

1. Routing

Route.classify reads a goal into a RouteKey:

  • Judgment head: core or VCVio triple, ⊑ wp, the relational judgments, =ᵈ, query and cost bounds, Foxglove entailments, or a relation. An equation at a monad type is an equation of programs.
  • Side kinds of a relation: event, measure, wp, expectation (∑′ or ∫⁻), coupling, total-variation distance, 0, 1, or arithmetic.
  • Carrier and interpretation of a triple. The reading is read off the WP instance, including a caller's own instance definition.
  • Monad and computation heads.
  • Premise bits: support membership, triples, query bounds.

It never searches the term, unifies, or tries a step speculatively. That is why it routes correctly the triples that sit in premises and the Prop and Prob carriers, which today's find?-based classifiers misroute.

What the probes found missing

  • Handler specs. WP-form specs for the caching, seeded and logging oracles; structural simulateQ specs; a whole-simulation monotone frame; a support_of_triple_wp bridge.
  • Reducibility. Reducible wrapper definitions, or one-step equation lemmas, because spec matching does not unfold wrappers.
  • Relational rules. The bisimulation equation simulateQ_run_eq_of_impl_eq_on_inv (proved in P2 in 7 lines), and a cross-type bijection coupling.
  • Bound readings. The upper reading restored, with simulateQ_triple_ranked and a StateT readback simp set; a budget reading for query bounds.
  • Tactic defects. rvcstep crashes on a loose bound variable; an untyped using hint is misread; a pure leaf with a non-EqRel relation fails instead of leaving its goal; rvcgen hits maximum recursion depth; swaps have no side or depth selector; the vcstep? planner is costly.
  • A core bug. An eta-reduced StateT precondition makes core vcgen fail.

3. Upstream: what core gives on v4.36

FeatureFinding
Framesworks A Foxglove-style ∗ rides core frames on v4.35, rc1 and the nightly. It needs an opaque assertion type, its own monad head, withFrameClosure, specs with concrete posts, and a roughly 75-line frameproc. One blocker: core does not expose the frame rule's WP.Frames side goal.
+jpnightly only 64 verification conditions collapse to 1. It shares nothing when preconditions carry resources, and errors on v4.35 and rc1.
Quantitative goalsstops at averaging Core handles pure, bind, if, ∧ splits and fixed-post specs. It stops at the first +, *, ∑ or ∑′, and its table of lattice operations is closed. Equational WP laws close what it leaves.
Bump readinessbuilds PolyFun and VCVio build on rc1 with small patches. Most of the breakage comes from Mathlib (Set is now a structure). The Std.WP changes: PolyFun's wpTrans is now a separate field, binders were renamed epost→eposts, and throws is a keyword. A hidden risk: a meta-level mkAppM call on a deprecated name in Backward.lean.

Requests to make of core

  1. Expose the WP.Frames side goal to frameprocs, or discharge it automatically.
  2. An extension point for lattice operations or steps, so a library can step through + and ∑.
  3. Spec arguments at a call site that may depend on earlier binders.
  4. +jp sharing with resource-carrying preconditions.
  5. The eta-reduced precondition bug.

5. Roadmap

  1. Land the route key, diagnostics and core-triple front end. It is small, has no measured overhead, and fixes misroutes.
  2. Add only the library rules with measured payoff (sections 2 and 6), then extend dispatch to the readings, the bisimulation rule and the budget reading.
  3. Fix the relational tactic defects.
  4. Bump to v4.36 from the rc1 patches when the release lands, and adopt +jp once it is in a release.
  5. Foxglove:
    • open the bridge PR (the VCVio switch), stacked on a cleaned-up v4.35 update, including Foxglove's notation scoping and the Countable generalization;
    • then try its ∗ on core frames;
    • raise iris-lean's global ⊤ notation upstream.
  6. Send the requests to core.
  7. Re-prove the routed proofs with today's tools (section 6). This is the largest measured saving: about 44% of the frame's lines.

6. Does a large spec library pay?

Sections 2 and 4 found missing specs in every probe. So we built the library they asked for and measured it on a random sample of the routed theorems. It does not pay. A careful re-prover with today's tools already removes 44% of the lines; the library adds about one point and costs more lines than it saves.

The sample is 20 routed theorems, seeded and stratified by family and length, with long proofs drawn proportional to size. The frame is 813 theorems and 22.9k census lines.

Each theorem was re-proved in a copy of its own file, with the statement checked unchanged and a heartbeat gate:

  • A: today's tools;
  • B: plus T1 and T2, starting from A (anything that didn't need the library went back into A);
  • C: plus T3 and the deriver;
  • F: a fresh agent with the library, never shown A.

The early stop triggered (increment < +3 points, upper bound < +10), so the 40-theorem main sample was not run. The fresh agent matched A–B. Heartbeats fall to 0.82× the originals in A and 0.78× in B. Importing the library costs about 1 heartbeat.

What the savings are made of

  • Statements are 19% of the lines, and nothing removes them.
  • Proof bodies shrink 75% with today's tools, for example 407 → 57, 213 → 35 and 47 → 2 lines. Tokens fall 54%, so this is not line-cramming.
  • The cuts come from dropping restated intermediate programs, normalizing in place with simp only while unification fills in continuations, using existing generic lemmas the originals missed, and collapsing repeated blocks.

What the library contributed

The re-proofs used only a handful of the ~430 new declarations:

  • the simulateQ_nf simp set, in 5 proofs;
  • two handler run_apply lemmas and StateT.run_ite;
  • T3's support iffs, in 1 proof.

No spec, frame, bridge, bisimulation rule, reading or bound was used. The wins were 18 → 13 lines, 16 → 10, 13 → 12, and two heartbeat halvings.

Specs did not bite for three reasons:

  1. The long proofs are about distributions, not supports: weighted sums over runs, lazy versus eager tables, frozen cache values, event bounds through map and bind.
  2. Normal-form defects:
    • monad laws don't fire on cslib's direct FreeM.instPure/instBind;
    • the simp set re-types answers of sum specs;
    • handler lemmas are stated on impl q s rather than .run.
  3. Placement: a scheme spec module must import its handler's file, so theorems in that file can't import it.

The deriver, measured over the whole census, covers 168 of 169 scheme handlers. Its derived lemmas prove 85 of 115 hand-written one-step equations, but plain simp already proves 81. Its value is removing statements: 834 census lines could become 42 one-line commands.

What to do instead

  1. Re-prove with today's tools: about 44% of the frame's lines, about 10k lines.
  2. Keep only what earned its keep: simulateQ_nf (plus missing members), the handler run_apply lemmas, and support iffs for handlers that proofs step through.
  3. Fix the normal-form defects above.
  4. Adopt derive_handler_specs for one-step equations.
  5. Add the few distribution-level theorems the pilot asked for, each justified by demand: a union bound through maps, a coupling bound through bind, a discard rule, identical-until-bad for full runs, event forms of the draw swaps, congruence of weighted sums, and lazy versus eager random oracles.

Caveats: n = 20; agent re-provers on one model, with timeboxes; the new proofs weren't reviewed for maintainability; future proofs and theorems outside the frame were not measured.
