# Inspecting the FIPS 205 SLH-DSA formalization

Start with the operation you want to inspect. The code separates the FIPS algorithms, their instantiation with hash functions, and security experiments that replace hashing with an ideal oracle. A signature that verifies after honest signing is a correctness result. A bound on an adversary producing a fresh verifying pair requires a security theorem and its resource hypotheses. [NIST FIPS 205, final](https://doi.org/10.6028/NIST.FIPS.205)

## From the standard to Lean

The names below are search terms in their linked source files. They identify definitions or characterizations of the algorithms. The conformance lemmas establish specific identities, lengths, positions or byte layouts. There is no single theorem of conformance to the complete standard.

## Choosing a security theorem

| What the caller knows | Entry point |
| --- | --- |
| A validated SHAKE parameter set, pure mode at a fixed valid context, and structural bounds on the adversary's hash and signing queries | Use `wireStrongAdvantage_le_securityBound_validatedParams` or its hedged counterpart. The structural analysis first separates the tweakable hash, message hash and message PRF. It accounts for these roles sharing byte inputs when it passes to a single SHAKE oracle. [Wire theorems](../../HashSig/SLHDSA/Security/Wire.lean) · [Bounds and coefficients](../design/slh-dsa-classical-rom-bound.md) |
| Deterministic SHAKE-128s, independent uniform key seeds, one shared 30-byte random oracle, per-request contexts, and an almost-sure work bound | Use `slhDsa_sufCma_le`. The cap adds signing attempts, direct adversary hashes and actual final-verifier hashes on each execution. Key generation and signing use the same oracle, but their hashes are excluded from the sum. The theorem assumes a signing lifetime of at most 2⁶⁴ attempts. Below 569, a separate zero-success theorem needs only the cap. [Actual-work theorems](../../HashSig/SLHDSA/SHAKE128s/Statement/Theorems/StrongUnforgeability.lean) |
| Deterministic SHAKE-128s, fixed valid context, structural caps and the signing lifetime | `wireStrongAdvantage_le_jointWorkBound` takes the smaller of the two estimates on the same advantage. Its work allowance includes up to 3,824 final-verifier hashes. [Combined theorem](../../HashSig/SLHDSA/SHAKE128s/Statement/Theorems/WireStrongUnforgeability.lean) |

The shared native construction and forgery classification feed two quantitative arguments. The structural route charges events against separate caps. The actual-work route keeps the terminal result, cache, signing log and costs together and bounds events using the work paid on that execution. The paper's 240-bit presentation receives the native result by transport. These bounds concern pure-mode signatures and classical random-oracle queries. HashSLH-DSA prehash framing has correctness and test coverage. A forgery bound for the external prehash interface remains open. [Joint-work proof guide](../design/slh-dsa-shake128s-suf-cma.md) · [Paper interface](../../HashSig/SLHDSA/SHAKE128s/Proof/WorkFinal.lean)

## SHA-2 parameter sets

For all six FIPS 205 SHA-2 sets, `Concrete.approvedPrimitives` selects `Concrete.sha2Primitives`. F and PRF always use SHA-256. At the arities used by the scheme, H and T_ℓ use SHA-256 for 16-byte nodes and SHA-512 for 24- and 32-byte nodes. The same width-dependent choice applies to HMAC in PRF_msg and to the inner hash and MGF1 in H_msg. The generic correctness theorem `GeneralScheme.verifyInternal_signInternal` proves that honest signatures verify under generated keys for every choice of seeds, message and randomizer. [FIPS primitives](../../HashSig/SLHDSA/Concrete/FIPS.lean) · [Internal correctness](../../HashSig/SLHDSA/GeneralScheme.lean)

The library records the profile's parameters and target caps for the FIPS SHA-2 family at it, and states no security bound there. The proved security bounds are the SHAKE random-oracle theorems in the table above. A reduction of SLH-DSA forgery to named hash-function assumptions in the standard model is research work on the branch `slhdsa/standard-model` and is not part of this library. ## Reading the source tree

- Begin in `GeneralScheme` for the standard. `Scheme` and `Hypertree` also expose a depth-one construction with a proved compatibility relation. [Depth-one compatibility](../../HashSig/SLHDSA/DepthOneCompatibility.lean)
- `Security` contains the structural reduction, component witnesses, concrete estimates and the byte-wire transport. `Security/Profile` provides a parameter- and mode-specific interface. `Graph` and `SecretProvider` support experiments which record hash inputs or change the source of secret values. [Profile interface](../../HashSig/SLHDSA/Security/Profile.lean) · [Profile and provider examples](../../Examples/SLHDSA)
- In `SHAKE128s`, start at `Statement/Theorems` for a result, `Statement/Game` for the success event and counts, and `Bridge` for representation and budget transport. `Proof/ActualWork` contains the execution accounting and probability argument. [Game](../../HashSig/SLHDSA/SHAKE128s/Statement/Game.lean) · [Proof families](../../HashSig/SLHDSA/SHAKE128s/Proof/ActualWork)
- `C13` is a separate Keccak-based variant with WOTS+C and FORS+C. Its parameter choices and known-answer test belong to that construction. [C13 parameters](../../HashSig/SLHDSA/C13/Params.lean) · [C13 regression](../../HashSigTest/SLHDSA/C13KAT.lean)

## Reproducing the evidence

`lake build HashSig` checks the proof library. `lake exe slhdsa_byte_model_tests` runs fifteen pinned NIST ACVP internal-interface records across SHAKE-128f, SHAKE-192f and SHAKE-256f, including deterministic and hedged signing and both accepted and rejected signatures. These records cover selected inputs. The general correctness and security claims above have their own quantified Lean statements. [Vector driver](../../HashSigTest/SLHDSA/ByteModel.lean) · [Fixtures and provenance](../../HashSigTest/SLHDSA/ByteModelVectors)

`lake test` includes the counted-game and wire-bridge executables, the exact coefficient-table comparison and the security contract checks. The examples illustrate how a downstream user can adapt a signing profile, FORS secret provider or cost policy.
